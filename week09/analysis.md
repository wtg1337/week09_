## 2. JTBD와 근거 구분

- 상황·하려는 일·현재 방법·불편·기대 효과:
  - **상황**: 등교 직후 또는 쉬는 시간에 다음 수업 강의실(건물 동·호수)을 확인하거나 지각·결석 사유 등으로 교수님께 급히 이메일을 보내야 하는 순간
  - **하려는 일**: 3초 이내에 정확한 강의실 위치와 교수님 이메일 주소를 확인하고 바로 메일 앱에 붙여넣기
  - **현재 방법**: 모바일 브라우저로 신구대 학사 포털 접속 → 로그인 → 시간표 조회 또는 강의계획서 PDF 다운로드 후 텍스트 복사
  - **불편**: 로그인 절차가 번거롭고, 강의계획서 PDF를 열어야 교수님 이메일을 확인할 수 있어 이동 중 빠르게 처리하기 어려움
  - **기대 효과**: 포털 로그인 없이 앱 실행 즉시 오늘 다음 수업 정보 카드를 확인하고 버튼 한 번으로 이메일을 복사해 지각 및 연락 지연을 방지함
- 확인된 사실과 위치: 신구대 학사 포털 및 강의계획서를 통해 시간표와 교수 연락처를 확인하려면 로그인 및 별도 문서 열람 단계를 거쳐야 함 (본인 실제 사용 경험)
- 개인 경험: 수업 직전 강의실 호수가 헷갈리거나 급히 교수님 이메일을 찾을 때 포털 로그인과 PDF 열람 과정에서 시간을 지체한 경험이 있음
- 가정과 직접 확인할 질문:
  - **가정**: 다른 학과 재학생들도 수업 직전 강의실 위치와 교수님 이메일을 자주 급하게 찾으며, 학기 초 1회 직접 입력 방식을 감수하고 쓸 것이라는 점은 아직 확인 전 가정임
  - **확인할 질문**: (1) 학기 중 교수님 이메일을 찾아야 했던 빈도가 얼마나 되는가? (2) 시간표 데이터를 직접 입력하는 방식과 스크린샷/메모 대비 얼마나 편리하다고 느끼는가?
- 중간 확인 1의 지적·수정 결과·확인 시점: 미확인 (교수님 확인 전 검토안)

## 5. 위험과 중간 확인 2

- 개발 시간·기술·저장·외부 의존·비용 점검:
  - 10~14주차(5주) 내 개인 개발 가능 범위로, 외부 API·서버·계정·비용이 전혀 없는 순수 오프라인 Flutter 앱이므로 외부 의존 위험이 없음
  - 단, 앱 재실행 후 데이터 유지를 위한 로컬 저장소(`shared_preferences` 또는 `sqflite`) 연동은 구현 전 검증 필요
- 줄일 기능과 유지할 핵심 가치:
  - **줄인 기능**: 주간 그리드 시간표 뷰, 학사 포털 크롤링, 수업 시작 푸시 알림
  - **유지할 핵심 가치**: 포털 로그인 없이 앱 실행 3초 만에 다음 수업의 건물·호수와 교수님 이메일(원터치 복사)을 확인하는 핵심 흐름 및 입력 검증·데이터 보존
- 교수님 지적·범위 수정·확인 시점: 미확인 (교수님 확인 전 검토안)
- 남은 질문·확인할 방법·담당·재확인 시점: 로컬 저장소 패키지(`shared_preferences` vs `sqflite`) 선택 및 테스트 · 본인 담당 · 10주차 개발 시작 전 확인
